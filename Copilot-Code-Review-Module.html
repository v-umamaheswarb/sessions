Code Review · 01

PR review and fix sessions

02 / 06

The review request and the follow-up code change are separate steps. Keep the PR timeline as the hand-off point.

01 · REVIEW

Request Copilot

Open the PR and add Copilot under Reviewers.

02 · INSPECT

Read summary + comments

Findings appear in the PR overview and on changed lines.

03 · HAND OFF

Fix with Copilot

Choose a review comment to start a cloud-agent fix session.

04 · VERIFY

Review the result

Check the diff and checks, then request a fresh review when needed.

Review session

Copilot assesses the PR and leaves a review summary with inline findings. By default, this is a Comment, not an approval.

Fix session

Fix with Copilot hands selected findings to a cloud agent. Review its proposed commit or PR; it does not merge for you.

For local, uncommitted changes, use the VS Code Source Control action Copilot Code Review - Uncommitted Changes. Use the GitHub PR review when PR context and its timeline matter.

Code Review · 02

Pick effort to fit the change

03 / 06

Review effort controls the depth of analysis. It is a choice for the review, not a guarantee that every issue will be found.

Lite Routine

Targeted feedback for a smaller, lower-risk change.

  • Look for common bugs, vulnerabilities, and style issues.
  • Useful when quick feedback is enough.
COMPARE

Balanced Default

Deeper analysis for complex or security-sensitive changes.

  • Uses more AI credits than Lite.
  • Useful for complex logic or changes across services.
A practical comparison

Verify findings

Balanced is the default in the source deck (as of 28 Sep 2026). Effort can be set per request; check your repository configuration.

Code Review · 03

MCP adds repository context

04 / 06

A review can use relevant read-only findings from tools such as issue trackers, SonarQube, or Wiz.

PR + instructionsDiff, issue key, review criteria
Repository MCPApproved, read-only tools
Grounded reviewRelevant external findings inform comments
Configure

Repository admin: Settings → Copilot → MCP servers.

Keep credentials in Agents secrets or variables named COPILOT_MCP_*, not in JSON.

Allowlist only tools the review needs.

Protect and verify

Code review filters out tools without readOnlyHint: true; do not expose write tools.

Open the review session from the PR timeline and inspect its session logs.

Confirm which MCP server and tools actually started and were called.

MCP review supports tools, not server prompts or resources. Remote MCP with OAuth is not supported for code review. Tool calls do not have a per-call approval prompt.

Code Review · 04

Run a review, then verify it

05 / 06

A short walkthrough with one routine PR and one complex PR makes the workflow observable without treating dissimilar changes as a benchmark.

01 · PREPARE

Check the setup

Confirm reviewer access, effort setting, instructions on the PR head branch, and MCP policy.

02 · REQUEST

Start the review

Open a PR and add Copilot under Reviewers. For drafts, confirm draft review is enabled.

03 · INSPECT

Read the evidence

Review the summary, inline comments, effort label, and MCP session logs if configured.

04 · CLOSE

Decide and verify

Validate each finding, run CI, and review any agent-created diff before merge.

Capture: PR type, effort selected, verified findings, missed issues, review time, and usage where available.

Keep human ownership: Copilot feedback is not proof of correctness. A review is not an approval unless policy explicitly enables it.

If a new commit needs another review, request one unless automatic review of new pushes is enabled.

Reference

Keep the review grounded

06 / 06

Use the source deck for the full setup details, policies, and examples.

PR sessions

Request a review from the PR, inspect the timeline, and use a separate Fix with Copilot hand-off for code changes.

Review effort

Use Lite for routine feedback and Balanced for deeper review of complex or sensitive changes.

MCP

Use repository-configured read-only tools, protect credentials, and verify actual tool calls in session logs.

Success looks like

Useful findings are verified, effort is chosen deliberately, MCP access stays read-only, and a person reviews every change before merge.
