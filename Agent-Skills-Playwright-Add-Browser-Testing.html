MODULE 1 · AGENT SKILLS

Customize Copilot
with skills.

Package team know-how so Copilot can discover and follow a specialized workflow when the task calls for it.

01
Definition

A small folder with a clear job

A skill centers on a SKILL.md file. YAML frontmatter gives it a name and a description of when it applies; the Markdown body contains the workflow. Scripts, templates, and examples can support it.

Problem it solves

Stop repeating tribal knowledge

Without a skill, people re-explain the project’s testing, deployment, or documentation process in each session. A skill makes that know-how reusable and discoverable.

Skills vs. instructions

Standards versus tasks

Instructions describe standards to follow, such as naming or formatting. Skills describe tasks to perform, such as running a browser-test workflow or generating release notes.

i

Module scenario: Customize Copilot with a reusable release-notes skill. The host matches a request against skill metadata and loads the workflow when relevant; the author defines the workflow.

your release-note process.

Create a focused skill and try it on a realistic task.

02
Project layout

Keep the workflow with the project

# Project skill location .github/skills/ └── release-notes/ └── SKILL.md # SKILL.md --- name: release-notes description: Draft release notes from merged PRs using our team format. Use when asked to prepare or update release notes. --- # Skill instructions 1. Review merged PR titles and labels. 2. Group changes by user impact. 3. Follow the team release-note template. 4. Flag unclear changes; do not invent details.
Demo

Create it, invoke it, inspect the result

1 · Create: Add .github/skills/release-notes/SKILL.md; keep the folder name and frontmatter name aligned.

2 · Customize: Describe the team’s output format, source material, and rules for missing information.

3 · Invoke: In a fresh Copilot chat, ask: “Draft release notes from the merged PRs for this release.”

4 · Review: Confirm Copilot followed the skill and did not invent details. Refine the description or workflow if discovery or output is off.

!

Module 1 outcome: The team leaves with a project-specific skill that customizes how Copilot handles one repeated task. Instructions remain the place for always-on standards.

MODULE 2 · END-TO-END TESTS

Add browser testing.

Use Playwright MCP to inspect and exercise a real browser, then keep the end-to-end check as a reusable test.

03
Definition

Browser tools over MCP

The server exposes tools to navigate, inspect page content, click, type, fill fields, and capture screenshots in a real browser.

Problem it solves

Build success is not user success

Compilation and unit tests cannot prove the interface works as a user experiences it. Browser interaction can verify a journey and reveal visible regressions.

How it sees

Structured page state

Accessibility-oriented snapshots expose controls and labels so the agent can act on page structure instead of relying only on pixels.

Local server configuration example
// .vscode/mcp.json { "servers": { "playwright": { "command": "npx", "args": ["@playwright/mcp@latest"] } } }
Key feature · Observe · Act · Verify

Browser exploration plus durable coverage

  • Observe: inspect the current page and controls.
  • Act: navigate and interact as a user would.
  • Verify: check the resulting state and report evidence.
  • Save a repeatable Playwright test and run it in CI.

Sources: Microsoft Playwright MCP · MCP servers in VS Code. For shared configurations, pin and review the server version according to team policy.

MODULE 2 · SCENARIO · ADD BROWSER TESTING

Turn a user journey
into a repeatable check.

Add end-to-end coverage for the local app’s contact form, then verify the journey in a real browser.

04
Ask Copilot

Add a browser test to this project

“Inspect this project’s existing test setup. Add a Playwright end-to-end test for the contact form: submit valid synthetic data and verify the success state. Use the local app only; do not send external requests.”

This is a standalone End-to-End Tests module; it does not depend on the Agent Skills module. Use a demo branch and inspect the repository before changing dependencies or configuration.

Live walkthrough

Inspect, add, run, verify

Inspect: Confirm the app starts locally and identify its existing test framework and form controls.

Add: Create or update a Playwright test using the project’s conventions. Prefer accessible labels and roles over fragile selectors.

Run: Start the app and execute the test. Use Playwright MCP to inspect and exercise the form if setup or failures need debugging.

Verify: Check the success message and test result; inspect any failure in the browser rather than guessing from source code.

!

Demo safety: Use a local or approved test environment and synthetic data. Avoid real accounts, production submissions, payments, external side effects, and sensitive information.
